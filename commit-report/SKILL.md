# Commit Report

用户这次没有明确要求写改动说明或工作汇报，就停。不要写文档，不要为了这两份文档去跑测试。

下面这些都不够，不要写：

- 提交代码、commit、帮我提交、准备 commit
- 提交已经做完，顺手补一份汇报
- 用户没提到这两份文档

够的说法：点名 `commit-report`，或直接说写改动说明、写工作汇报、写这两份文档。

在当前项目 `docs/changes/` 下新建日期文件夹，写入两份各自能独立阅读的 Markdown：

1. **详细版**（开发者）：哪个文件改了什么、行为怎么变、测试原文、怎么回滚。
2. **汇报版**（主管）：正文是效果、原因、改动三块，格式参照 `ainpc-inspiration-pipeline/docs/changes/prelabel-句式多样性.md`。效果用改动前 / 改动后的数字表，原因只说根因，改动用一行一个的表。正文之后接第四块**测试明细**：把完整的测试内容原样列出，一条一行（输入、改动前输出、改动后输出、留空的人工判断），再单列失败和异常、没测的项，让读者能不靠结论自己逐条检查。不贴实现代码，不堆函数名，不写测试章节和回退章节（这些在详细版里）。

详细版按其模板写，不压缩。汇报版正文压到一屏半以内；测试明细不受这个限制，但只放原始内容，不写解读。项目里如果已有更长的旧汇报，不要模仿它的篇幅。

## 写之前读

1. 读 [references/charts.md](references/charts.md)，按里面的规则选图。图必须能在老版本 markdown 和旧 mermaid 里渲染：只用顶格的 `graph`，不用 `flowchart`、`xychart-beta`、`quadrantChart`。
2. 详细版按 [references/template-detailed.md](references/template-detailed.md)，汇报版按 [references/template-report.md](references/template-report.md)。
3. 读 `C:/Users/yanxuxi/.agents/skills/Humanizer-zh-main/SKILL.md` 的「编辑约束与优先级」「文体与作者声音」「模式的使用方式」和「交付前核对」。直接按那个标准写，不要先堆套话再改。不要把 Humanizer 的教学示例抄进文档，也不要在文档里提到 Humanizer。

文体：详细版是技术说明，术语、条件、顺序、命令留着。汇报版是业务说明，用完整句，但不要公文腔（「现将……汇报如下」这类开头不要）。两份都保持不确定程度：没跑的写「未执行」，样本少就写样本数，不要把「可能」写成「已经」。

## 流程

### 1. 收集改动

- 未提交：`git status`，`git diff`（含已暂存）。需要时再读改动文件里真正变了的段落。
- 多个提交：`git log --oneline <范围>`，再逐个 `git show --stat`。
- 记下：日期、分支、提交（或「未提交」）、文件清单（新增 / 修改 / 删除分开）。
- 只写这一次的改动。

### 2. 跑测试，记下原文

两份文档都靠这一步，不能跳。

- 用项目实际的命令跑全量测试。
- 记下命令和原始摘要（例如 `14 failed, 953 passed, 207 errors`），不要改写数字。
- 仓库里改动前就失败的用例：先确认基线失败集，再对比。结论只写「失败集与改动前一致」或列出新失败。
- 本次新增或修改的测试：文件、条数、各自验证什么。
- 有离线统计、前后对比、真实模型抽检时，记下方法和数。样本少于 10 时不要画趋势，逐条列表，并写明样本数。
- **每一条测试的原始输入和原始输出都要留下来**，不只是汇总数字。汇报版的测试明细要逐条列出，事后补不出来；输出一字不改，失败、报错、返回为空、被兜底的条目也要记下原始信息。
- 没跑的项写「未执行：<哪一项>」。不编造数字，不补一张「示意」图。

### 3. 写两份文档

- 文件夹：`docs/changes/YYYY-MM-DD/`。当天已有同名文件夹时用 `YYYY-MM-DD-2`。
- 详细版：`docs/changes/YYYY-MM-DD/YYYY-MM-DD-<主题>-detailed.md`
- 汇报版：`docs/changes/YYYY-MM-DD/YYYY-MM-DD-<主题>-工作汇报.md`
- 两份文档各写各的，数字可以重复，因为读者可能只看一篇。同一份里不要又画条形又贴一张同数据的表，条形下也不要再列一遍。
- 详细版有对比数字的小节：先写结论，关键的那一个对比可以出现在这句话里，然后放条形表。表下最多一句，只补表上没有的判断。
- 汇报版的对比数字用**纯数字表**（改动前 / 改动后两列），不画条形，不画 `graph`。表怎么分组、怎么标样本规模，按 [references/template-report.md](references/template-report.md)。
- 汇报版不出现函数名、配置键和命令。业务上绕不开的术语，第一次用中文说明。
- 详细版里行为变化才用 `graph`。节点只说一件事，不超过 20 字。图里放不下的细节写在图下面的列表里，不能为了兼容丢掉。

### 4. 落盘前核对

- 每个数字都能在测试输出、diff 或用户材料里找到。
- 否定、范围、样本量和「未执行」都还在。
- 只剩赞美、没有新事实的句子删掉。工程术语留着，例如闭环控制。
- 条形和 `graph` 在表达一件实测的事。没有数字的装饰图不要。
- 回滚步骤能直接执行。
- 详细版保留了测试命令的原始摘要和前后对比的条形表。汇报版没有单独的测试章节，对比数字放在「效果」表里；没跑实测对比时，「效果」一节写「未执行：<哪一项>」，不编数字。
- 汇报版正文只有标题、效果、原因、改动四块，一屏半以内，多出来的细节删掉，让详细版去承载。正文之后是「测试明细」：核对它和「效果」是一回事，效果表里的每个数都能在明细里数出来；输出是原样的、没有被润色；「人工判断」列是空的；失败和异常单列，没有失败也写了「没有失败」；没测的项写了「未执行」。
- 对两份文档跑自检，ERROR 清掉，WARN 也清掉。文档可能贴到旧编辑器或内部 wiki。数值为 0、图示写成「无」时，脚本对这一行的 WARN 可以留，不要为了消警告画 1 格。

```powershell
python C:/Users/yanxuxi/.agents/skills/commit-report/scripts/check_md_diagram.py <详细版.md> <汇报版.md>
```

脚本退出码 0 表示没有 ERROR。规则和 `md-diagram-safe` 相同，检查器放在本 skill 里，不依赖另一个 skill 是否装上。

### 5. 告诉用户

把两个文件的绝对路径发出来，并说明这两份文档还没进提交，要不要一起 commit 由用户决定。
